# Per-language governed memory — export bundles

These JSON bundles are the **governed institutional translation memory** for each
target locale, exported for a build team. Each bundle is the curated, auditable
asset that makes output high quality — **not** machine-translation output and
**not** the offline demo fixtures.

Generated by [`scripts/export-memory.mjs`](../../scripts/export-memory.mjs) from the
committed source files. Re-run any time with:

```bash
node scripts/export-memory.mjs
```

## Files

| File | Locale | TM | Glossary (applied) | Neutralization rules (applied + queued) |
|------|--------|----|--------------------|------------------------------------------|
| `es-419.memory.json` | Spanish, neutral Latin American | 6 disclaimers | 22 | 6 + 3 proposed |
| `zh-Hans.memory.json` | Chinese, Simplified | 13 disclaimers | 52 | 0 |
| `zh-Hant.memory.json` | Chinese, Traditional | 18 disclaimers | 50 | 0 |
| `index.json` | manifest | — | — | per-bundle counts + content hashes |

Each bundle embeds its own `meta` (provenance, counts, a field dictionary, the
lifecycle legend, and `gaps`), the three governed collections, and the applied
locale config.

## What's inside each bundle

- **`translation_memory`** — approved source→target segment pairs. All current
  entries are `kind: disclaimer` (compliance boilerplate), which the pipeline
  routes separately and excludes from few-shot retrieval. No few-shot example
  pairs are seeded yet; they grow via the Train page / "Send to memory" flows.
- **`glossary`** — approved term mappings with `forbidden_terms`, split into
  `applied` (state `active`/`approved`) and `governance_queue` (everything else).
- **`neutralization_rules`** — regional→neutral rewrite rules, same `applied` vs
  `governance_queue` split.
- **`locale_config`** — the applied `config/locales/<locale>.yml`. This is config,
  not lifecycle-governed memory, but it drives quality: `scale_terms` (the
  **billion = 10⁹ = "mil millones", never "billón"** trap), number format,
  register, `regional_flags`, morphology, and the language-specific prompt clauses.

## Governance contract — read before applying (ADR 0008)

Only entries with state **`active`** or **`approved`** are applied by the pipeline
(`src/memory/apply.ts`). Entries under any **`governance_queue`** are **not
applied** and must not be folded into a live system without approver/admin
sign-off. The memory never changes silently from a raw edit — corrections flow
through the governed propose→approve lifecycle (`/api/memory/proposals`).

## Known gaps (honest provenance)

- **No neutralization rules exist for zh-Hans or zh-Hant** (empty). Any
  reviewer-flagged neutralization knowledge that has not been approved is **not**
  captured in these bundles — it must pass through the governed propose→approve
  lifecycle first. Do not hand-author rules into a live system; route them through
  governance.
- **es-419 carries 3 `proposed` rules** (`nr-007`–`nr-009`) in the governance
  queue — present for visibility, **not** applied.
- **TM is disclaimers only** across all three locales, so these bundles supply
  reusable compliance boilerplate but no few-shot translation examples yet.

## Deliberately excluded (not governed memory)

`glossaries/fixture-translations*.json` (offline no-key demo dictionary, ADR 0013),
`config/models.yml` · `permissions.yml` · `thresholds.yml`, `supabase/schema.sql`
(DDL), `evals/**` (test fixtures), and `.context/plans/**` (ungoverned planning
corpora).
